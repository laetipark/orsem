# 2026-10-09 재부팅·502 장애 조사

시각은 KST입니다. 아래는 2026-10-09 조사 시 확인한 사실과 적용 절차이며, PC의 물리적 안정성이나 재부팅 후 결과까지 검증했다는 의미는 아닙니다.

## 확인한 원인과 한계

- 10월 7일 04:58과 19:22의 crash dump에 Linux `6.8.0-139-generic` 커널 충돌이 기록되었습니다. 각각 `scheduler_tick`/`srso_safe_ret`와 `pick_next_task_fair` 경로이며, 두 충돌 모두 CPU 5에서 발생했습니다. 당시 실행 중이던 프로세스 이름만으로 해당 앱이 커널 충돌을 일으켰다고 판단할 수 없습니다.
- 조사한 기록에는 OOM, 디스크 I/O 오류, 열로 인한 종료의 증거가 없었습니다. 검사 시 여유 메모리·디스크 공간도 충분했습니다. 하드웨어 결함과 커널 버그 중 어느 쪽인지 확정하지 못했습니다.
- 기존 `orsem-cpu-isolation.service`는 CPU 5와 11(동일 물리 코어의 SMT 쌍)을 끄도록 설정되어 있지만, `Device or resource busy`로 실패했습니다. 도우미가 실패 시 원래 상태로 되돌려 현재 모든 CPU가 online입니다. 기존 무결성 검사 대상인 도우미를 직접 수정하지 않습니다.
- 커널 `6.8.0-142-generic`이 설치되어 있지만, 진단용 GRUB 설정이 139를 고정했습니다. 검증된 142 부팅 항목으로 변경해 다음 부팅에서 사용할 수 있습니다. 이 변경만으로 결함이 해결된다고 보장하지 않습니다. crash dump 수집과 panic 설정은 유지합니다.
- 10월 9일 01:27 기록은 로그인 세션 시작이며, 최신 실제 OS 부팅은 10월 7일 19:22입니다.
- Redis 로그에는 `appendonly.aof.415.incr.aof`의 형식 손상과 반복 시작 실패가 있습니다. 커널 충돌은 저장 중단을 일으킬 수 있으나, 이번 파일 손상의 직접 원인까지 입증되지는 않았습니다.
- Nginx의 웹 문서 응답은 200이지만 API 세션·준비 상태는 502였습니다. API 시작 시 Redis 연결 실패가 처리되지 않은 Promise rejection으로 남아 PM2 `online` 상태에서도 HTTP 포트를 열지 않는 문제가 있었습니다. worker는 PID 0의 `waiting restart` 상태였습니다.

## 코드 개선

API 시작 실패 시 제한 시간 내 정리를 마친 뒤 종료 코드 1로 종료합니다. 부팅·주기 복구 작업은 실제 Redis 연결과 API 응답을 확인하고 Orsem 프로세스만 처리합니다. 의존 서비스가 중단된 동안 반복 재시작하지 않습니다.

웹은 첫 접속 장애를 한국어로 안내하고 5·10·20·30초 간격으로 재연결합니다. 세션 요청은 15초 제한을 두며, 일시 장애에서 이미 확인한 화면을 유지합니다. 복구 후 실패한 활성 조회를 다시 수행합니다. 명시적인 401/403 응답은 기존과 같이 보호 화면을 차단합니다.

## Redis 복구와 호스트 설정

`scripts/repair-host-runtime.py --help`로 적용 옵션을 확인합니다. 실제 적용에는 관리자 권한이 필요합니다. 스크립트는 Redis가 중단된 상태에서 전체 데이터와 설정을 저장소 밖 비공개 경로에 백업한 뒤 복구하며, 예상과 다른 저장 경로나 설정은 작업을 중단합니다. AOF 복구는 명시적인 옵션을 주었을 때만 수행합니다.

프로젝트 루트에서 실행하는 한 번의 관리자 명령입니다. `sudo` 암호는 사용자의 터미널에서만 입력합니다.

```bash
sudo python3 scripts/repair-host-runtime.py --apply --repair-aof --update-ga-kernel
```

**AOF 복구는 손상 지점 이후 기록을 잘라낼 수 있습니다.** 백업을 삭제하지 말고, 복구 후 세션·큐·최근 작업 상태를 확인해야 합니다. Redis 공식 문서도 복구 전 백업을 요구합니다. 더 강한 내구성을 위해 `appendfsync always`를 사용하면 쓰기마다 동기화하므로 처리 속도가 낮아질 수 있습니다. [Redis persistence](https://redis.io/docs/latest/management/persistence/)

관리자 스크립트는 Redis 설정을 보존하면서 내구성 옵션과 `vm.overcommit_memory=1`을 적용합니다. 커널 선택 변경은 별도 옵션이며 이미 설치된 정확한 이미지·initrd·모듈·GRUB 항목을 확인합니다. 자동으로 PC를 재부팅하지 않습니다. CPU 격리 재시도가 실패하면 해결되지 않은 항목으로 출력합니다.

## 복구 후 확인

1. `redis-server`가 active이고 AOF 오류가 새로 발생하지 않는지 확인합니다.
2. `/api/v1/health/ready`와 `/api/v1/auth/session`이 200을 반환하는지 확인합니다.
3. API·worker의 실제 실행 상태와 기존 큐 작업을 확인합니다. Redis 데이터를 초기화하거나 fixture를 넣지 않습니다.
4. 다음 계획된 부팅 후 실행 커널과 CPU 격리 상태를 확인합니다. 같은 CPU에서 충돌이 재발하면 BIOS·CPU·RAM을 포함한 별도 하드웨어 진단이 필요합니다.

웹·API·crontab 백업은 `../orsem-data/backups` 아래에 보관합니다. 관리자 스크립트의 Redis·시스템 설정 백업은 별도의 root 전용 시스템 백업 디렉터리에 생성되며, 실제 위치는 `Full private backup` 출력으로 확인합니다. 롤백은 해당 백업의 설정과 실행 파일을 사용하되, Redis가 실행 중일 때 데이터 파일을 덮어쓰지 않습니다.

## 이 작업에서 확인한 적용 상태

- 웹과 API 시작 실패 처리 파일을 별도 작업 복사본에서 빌드한 뒤 기존 실행 파일을 백업하고 반영했습니다. 웹의 이전 해시 자산은 유지했습니다.
- 기존 crontab을 보존하면서 Orsem 부팅 항목 하나와 2분 주기 복구 항목 하나를 설치했습니다.
- 웹 관련 테스트 43개, 부팅 테스트 25개, API 시작 실패 테스트 2개, 관리자 복구 스크립트의 오프라인 테스트 20개와 타입 검사·빌드가 통과했습니다.
- 실제 HTTPS 웹 파일이 배포 산출물과 일치하고, 브라우저에 재연결 안내가 표시되는 것을 확인했습니다.
- Redis 중단 중 `--recover`를 실행했을 때 실패 상태를 반환하고 PM2 프로세스를 변경하지 않는 것을 확인했습니다.
- 이후 사용자가 관리자 복구 명령을 실행하여 전체 백업, AOF 검사·복구, 저장 설정 강화, 다음 부팅 커널 선택 변경, CPU 격리, Redis·Orsem 시작까지 성공했습니다. 출력된 비공개 백업 디렉터리 이름은 `repair-lvhv2pi6`입니다.
- 복구 후 실제 호스트에서 웹 `/`, `/api/v1/auth/session`, `/api/v1/health/ready`가 모두 HTTP 200을 반환하는 것을 확인했습니다. Redis는 active이고 API·worker·Discord는 실제 PID가 있는 online 상태입니다.
- CPU online 목록은 `0-4,6-10`으로 CPU 5·11 격리가 적용되었고, `vm.overcommit_memory=1`입니다. 현재 실행 커널은 139이며 142 선택은 다음 부팅에 적용됩니다. 다음 부팅 후 격리 유지와 장기적인 커널 충돌 재발 여부는 아직 확인하지 않았습니다.
