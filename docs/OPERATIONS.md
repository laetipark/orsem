# 운영

## Python 워커 실행과 점검

Python 3.12 워커와 관리 CLI의 전환 상태는 [현재 배포 상태](DEPLOYMENT.md#python-워커-전환-상태)를 확인합니다. PM2는 `../orsem-data/worker/current/bin/python -m orsem_worker`를 직접 실행합니다. API·웹·Discord는 기존 TypeScript 프로세스를 유지합니다.

개발·격리 후보의 설치와 검사 명령은 [Python 워커 안내](PYTHON_WORKER.md#실행-환경)를 따릅니다. 운영 관리 명령은 설치된 wheel을 직접 실행합니다. `scripts/worker.py`와 파서 스크립트는 저장소 소스를 불러오는 개발용 진입점이므로 운영 Python 경로만 지정해 배포본이라고 간주하지 않습니다.

```bash
export ORSEM_REPO_ROOT="$PWD"
../orsem-data/worker/current/bin/python -I -B -m orsem_worker.cli collect-sec --status
```

`collect-sec --status`는 저장된 상태를 조회합니다. ETF·시장 후보 조회는 공급자 요청을 포함하며, `--apply`가 있는 명령은 지정한 DB 자료를 변경합니다. 실제 SEC 수집·검증과 파서 감사·staging·백업 명령의 범위는 [Python 운영 CLI](PYTHON_WORKER.md#운영-cli)를 참고합니다. 비밀 값은 기존 외부 환경 파일로 주입하고 감사 산출물·원문은 저장소 밖에 보관합니다.

배포 전에는 `python3 scripts/verify-in-isolation.py`로 검사·빌드를 격리합니다. 운영 `dist` 또는 `../orsem-data/worker/current` 환경에 검사 산출물을 덮어쓰지 않습니다. 재시작 전 큐의 기존 정지 상태를 기록하고 활성 작업이 끝나는지 확인합니다. 워커는 모든 큐 수신과 주기 작업을 중지한 뒤 최대 10분 동안 실행 중인 작업을 기다리며 PM2 종료 유예는 11분입니다. 체크포인트·DB outbox·일반 큐 작업을 지워 재시도를 초기화하지 않습니다. worker만 복구하는 절차와 외부 보존 경로는 [전환과 복구](PYTHON_WORKER.md#전환과-복구)를 따릅니다.

종목별 알림 선택은 개인 계정의 설정입니다. 개별 설정이 없으면 월간 시총 선정 종목 범위를 상속합니다. 종목별 ON/OFF는 이 종목 범위만 바꾸며, 전체 알림 활성화·주제·공시 유형·계정 권한은 계속 적용합니다. Python 워커는 알림 후보 생성과 실제 Web Push 전송 직전에 이를 다시 확인합니다. 개인·공유방 관심 그룹 편집과 별개이며 종목 알림을 켜도 수집 범위를 자동으로 확대하지 않습니다.

## 조건부 뉴스 확장 운영 (2026-09-07)

이번 확장은 운영 수집을 자동으로 켜지 않는다. `MARKETAUX_NEWS_ENABLED`, `ALPHAVANTAGE_NEWS_ENABLED`, `FINNHUB_NEWS_ENABLED`는 모두 false다. 키만 추가해도 요청하지 않는다. 코드의 공급자 권리, `APPROVED_FREE_NEWS_ACCESS`의 무료 이용 확인 만료일·entitlement, 정확한 원출판사별 정책을 모두 승인해야 한다. Finnhub는 계정에서 확인한 분당 요청 한도도 필요하다. 유료 플랜/요금 청구로 자동 전환하지 않는다.

이 숫자는 Orsem의 보수적인 설정값이다. 공급자의 공표 한도와 동일시하지 않는다. 실제 무료 한도는 [최신 비교](NEWS_PROVIDER_COMPARISON.md)를 참고한다. 기존 BullMQ 수집 작업을 사용하며 신규 큐나 별도 cron 서비스는 없다. 관리자 소유 개인 그룹만 초기 API 범위에 포함하고 회원·관심방 수집 범위를 섞지 않는다.

각 HTTP 시도 **전** 기존 `source_checkpoints`의 `NEWS_API_BUDGET` 행을 잠가 최근 24시간 예약·cooldown·분당 한도를 검사하고 `api_usage_counters`의 UTC 날짜 카운터를 증가시킨다. 실패·timeout도 호출을 소비한다. 재시작하거나 중복 작업이 들어와도 예산을 초기화하지 않는다. 응답과 관련 기업을 저장한 뒤에만 기존 복구 checkpoint를 commit한다. 무료 한도 때문에 완료하지 못한 page/window는 미완료로 남기고 다음 실행에서 복구한다. 공급자 변경 fallback은 없다.

401은 인증, 403은 entitlement, Marketaux 402는 일일 한도, 429는 속도 제한, 5xx는 공급자 장애다. timeout·잘못된 JSON/XML·반복 pagination도 완료로 표시하지 않는다. API 키·전체 요청 URL·응답 전문은 로그/상태에 넣지 않는다. 관리자의 기존 소스 화면에서 활성화 상태, 최근 성공/실패, 다음 실행, 일일·최근 24시간 예산/사용량, cursor, 권리·entitlement를 확인한다. health 조회는 외부 API를 호출하지 않는다.

신규 RSS URL은 코드의 정확한 프로필과 host allowlist에 등록된 것만 사용한다. NVDA·AVGO·PANW와 한국경제 증권 프로필은 disabled/UNKNOWN이다. IR 등록은 현재 상장 company master와 프로필의 심볼·미국 시장이 일치해야 하며, URL을 선택하는 행위는 권리 승인이 아니다. 미등록 URL, HTML 대체 수집, redirect, 압축 응답, XML 이외 content-type은 허용하지 않는다. 승인 전에 실제 XML MIME/응답 구조도 소량 수동 확인해야 한다.

`AddNewsTitleHash1788413000000`은 2026-09-07 12:32 KST 운영에 적용했다. nullable 제목 해시와 인덱스만 추가하며 본문 backfill·전체 기사 재분류·신규 테이블은 없다. 기존 `synchronize=false`를 유지한다. 비밀 파일·운영 산출물과 분리된 `../../../tmp` 복사본에서 검증한 뒤 이번 뉴스 확장과 자동완성 변경만 선별 배포했다. 기존 SEC·GDELT 수집 동작을 보존하고 신규 공급자는 모두 비활성으로 유지한다. 소스 전체 빌드에는 다른 미배포 변경도 포함되므로 재배포 시 [배포 기록과 명세](DEPLOYMENT.md)를 대조한다.

2026-09-07 12:49 KST에 새 키로 세 뉴스 API를 각각 한 번 수동 점검해 HTTP 200·뉴스 목록·필수 필드를 확인했다. 요청은 기존 예산 카운터에 포함했고 응답 전문·기사는 저장하지 않았다. API·worker를 다시 시작해 환경 파일을 불러왔으며 신규 뉴스 수집은 비활성으로 유지했다.

남은 수동 확인 목록: 세 API 계정의 무료 플랜·이용 확인 기한, Marketaux 한국 심볼 coverage, Finnhub Company News 무료 entitlement·분당 한도·보존 종료 조건, provider와 정확한 원출판사의 영속 metadata·AI/번역 권리, 각 IR/RSS 권리. Business Wire·GlobeNewswire의 feed 계약과 한국경제TV의 공식 XML 주소가 확인되기 전에는 소스를 등록하지 않는다. 원출판사 권리를 철회하면 공급자 기본 정책을 먼저 차단하고 저장된 사본의 접근을 재검토한다.

`FSC_API_KEY`는 기존 금융위원회 조회 코드용 변수이나 현재 월간 시총 선정 경로에서는 사용하지 않는다. 국내·미국 월간 목록은 토스만 사용하므로 키 등록을 금융위원회 연결 또는 가격 공급자 활성화로 해석하지 않는다.

시장 지표의 공급원, 무료 키 발급, 1분 시세·6시간 이력 수집 및 지연 표시는 [시장 지표 운영](MARKET_INDICATORS.md)을 참고합니다. 공통 footer의 신선도는 저장된 상태만 조회하며 외부 API 점검을 실행하지 않습니다.

## 토스증권 차트 설정

1. 토스증권 WTS의 **설정 → Open API**에서 클라이언트 ID와 시크릿을 발급하고, **허용 IP 관리**에 이 서버의 외부 통신용 공인 IP를 등록합니다.
2. 자격 증명은 저장소 밖에 보관합니다. 예를 들어 `../orsem-data/toss-credentials.json`을 만들고 파일 권한을 `0600`으로 설정합니다.

   ```json
   { "clientId": "YOUR_CLIENT_ID", "clientSecret": "YOUR_CLIENT_SECRET" }
   ```

3. 서버 환경에 `MARKET_DATA_PROVIDER=toss`를 설정하고, 프로젝트 루트에서 `realpath ../orsem-data/toss-credentials.json`으로 구한 경로를 `TOSS_CREDENTIALS_FILE`에 지정합니다. 또는 프로세스 환경에 `TOSS_CLIENT_ID`와 `TOSS_CLIENT_SECRET`을 직접 주입합니다. 자격 증명에 `VITE_*`를 사용하면 안 됩니다. 두 방식 모두 유효한 자격 증명을 제공하지 않으면 토스를 비활성화하며, 환경에 주입한 값이 파일보다 우선합니다.
4. 처음 설치하거나 코드·스키마가 변경됐다면 격리 검증 후 배포 명세의 마이그레이션과 실행 파일을 적용합니다. 자격 증명만 변경한 경우 빌드·마이그레이션은 생략하고 큐 작업 종료를 확인한 뒤 관련 프로세스의 환경만 다시 불러옵니다.

   ```bash
   python3 scripts/verify-in-isolation.py
   ```

5. [배포 절차](DEPLOYMENT.md)에 따라 API와 Python 워커를 시작한 뒤 기존 기업을 엽니다. 과거 일봉·분봉을 요청하고 해당 기업을 실시간 구독에 일시적으로 추가합니다. 관심 목록의 P1/P2 기업은 자동 수집합니다.
6. 운영 화면의 토스 상태를 확인하고 실제 공급자 시각과 시장별 봉을 하나 이상 비교한 뒤, 거래 시간 중 새 체결 수신을 확인합니다. 빌드 성공이나 OAuth 토큰 발급만으로 실시간 수신이 입증되지는 않습니다.

기업 페이지가 보이는 동안 현재가와 선택한 차트를 2초마다 조회합니다. 분봉 화면은 이벤트 수익률과 마커 목록에 필요한 일봉도 갱신합니다. 타임라인 요청은 저장된 데이터를 반환하고 갱신 작업을 큐에 넣습니다. 2초 조회 주기는 새로운 공급자 값이 2초 안에 도착한다는 보장이 아닙니다. 큐 대기, 재시도, 시장 거래 여부가 신선도에 영향을 줍니다.

국내 종목(KRX·KOSPI·KOSDAQ·KONEX)에 오늘 KST 기준 체결가가 없으면 기업 상세·관심목록에서 **최근 거래일 종가**와 실제 기준 날짜를 표시합니다. 오늘 이전의 최신 저장 `TOSS_KR` 일봉 중 `PRIVATE_DISPLAY_ONLY` 권리의 양수 종가만 사용하므로 주말·휴일에도 달력상 어제 값을 임의로 만들지 않습니다. 당일 체결가는 지연 상태여도 우선하며, 당일 미완성 일봉과 미국 종목은 이 대체 표시에서 제외합니다. 저장 종가가 없으면 기존 시세 대기 상태를 유지합니다. 종가에는 과거 체결의 등락률이나 실시간 표시를 붙이지 않습니다. 2026-09-05 23:36 KST 운영에 반영했으며, [배포 기록](DEPLOYMENT-2026-09-05.md)에 실제 조회·화면 검증과 복구 위치를 남겼습니다.

최초 조회는 한도가 있는 과거 이력을 불러옵니다. 일봉은 366일 이내 최대 400개, 분봉은 7일 이내 최대 1,000개입니다. 이력 수집 성공을 봉과 함께 기록하며, 이후 조회는 최신 봉 페이지만 가져옵니다. 조회 사이의 간격이 길면 이력을 다시 수집합니다. 고정된 작업 ID로 대기·실행·지연 중인 갱신을 합치고, 완료되거나 최종 실패한 화면 조회 작업은 제거해 이후 조회가 새 작업을 등록할 수 있게 합니다.

마이그레이션은 가격 봉 고유 키에 소스를 추가하고 null이 가능한 소스 메타데이터를 추가합니다. 기존 가격을 대체하거나 기존 기록에 없던 메타데이터를 만들어내지 않습니다. 차트는 토스만 사용하며 이전 기록 선택 기능은 종료되었습니다. KRX·Alpaca 가격 정리는 스키마 마이그레이션과 별도로 수행하고, 해당 가격 봉·가격 작업·가격 수집 상태로 범위를 제한합니다. 기업 식별 정보, 공시, 뉴스, 각 소스 기록은 별도 도메인입니다. `legacy`는 공급자 설정 값으로 허용하지 않습니다. 여러 공급자의 봉이 같은 시각에 저장된 뒤에는 소스 보존 마이그레이션을 되돌리지 않습니다. 해당 상황의 롤백은 데이터 삭제를 막기 위해 거절됩니다.

worker는 REST와 WebSocket에서 OAuth 토큰 하나를 공유하고 설정된 애플리케이션 접두사 아래 Redis에 캐시합니다. 토스는 새 토큰을 발급할 때 이전 토큰을 무효화하므로 발급을 순차 처리합니다. WebSocket은 갱신 가능한 대표 작업자 점유권을 사용하고, 연결이 끊기면 다시 구독하며, 60초마다 `PING`을 보냅니다. `TOSS_MAX_SUBSCRIPTIONS`는 한 연결의 구독 기업 수를 1–100개로 제한하며 기본값은 100입니다. 설치별로 서로 다른 `REDIS_PREFIX`를 유지하고, 같은 토스 자격 증명을 사용하는 별도 클라이언트를 조정 없이 실행하지 않습니다.

토스의 허용 IP에는 서버가 실제로 사용하는 공인 IP를 등록합니다. 유선·Wi-Fi가 서로 다른 인터넷 회선을 사용하면 부팅 또는 장애 전환 중 공인 IP가 바뀔 수 있습니다. 등록되지 않은 보조 회선은 기본 경로가 되지 않도록 설정하거나, 운영자가 해당 회선을 확인한 뒤 허용 IP를 관리해야 합니다. [토스 공식 연결 안내](https://openapi.tossinvest.com/openapi-docs/overview.md)에 따르면 미등록 IP의 REST·WebSocket 연결은 HTTP 403으로 거부됩니다.

worker는 HTTP 403 또는 OAuth 클라이언트 인증 거부를 받으면 같은 자격 증명을 사용하는 REST·WebSocket 요청을 함께 중단합니다. 차단 사유는 토큰 캐시 키의 `:access-block` 항목에 저장되며 프로세스 재시작 후에도 유지됩니다. 일반 REST·WebSocket HTTP 401은 토큰을 한 번 갱신하고, 다시 거부되면 5분간 요청을 쉬었다가 자동으로 재시도합니다. 오류 로그에는 고정된 사유만 남기며 공급자의 응답 본문이나 토큰은 기록하지 않습니다.

영구 차단을 해제하려면 먼저 공인 IP·토스 WTS의 **설정 → Open API → 허용 IP 관리**·클라이언트 상태를 확인합니다. 워커를 정상 종료한 뒤 현재 설정의 `TossClient.access_block_key`에 해당하는 Redis 항목만 삭제하고 다시 시작합니다. 메모리에 보존한 차단도 초기화해야 하므로 Redis 항목 삭제만으로 실행 중인 워커가 재개되지는 않습니다. 다른 설치의 키 또는 Redis 전체를 삭제하지 않습니다. 자격 증명을 교체하면 새로운 자격 증명에 해당하는 별도 키를 사용합니다.

새 구독은 최초 REST 가격 스냅샷을 받은 뒤 WebSocket 체결 갱신을 수신합니다. 실시간 시세는 유실 가능한 스냅샷이며 완전한 체결 장부가 아닙니다. 화면은 공급자·관측 시각이 최신 상태를 유지하지 못한 채 15초가 지나면 시세를 지연 상태로 표시합니다. 휴장이나 거래가 드문 시간에도 이 상태가 나타날 수 있습니다. 캐시된 시세는 최대 하루 보관하므로 마지막 시세가 지연 상태로 계속 표시될 수 있습니다. 표시하는 OHLCV의 기준은 REST 봉입니다. 일봉 거래일은 해당 시장의 시간대(미국 주식은 뉴욕)를 사용하며, 분봉 시각은 UTC로 저장하고 KST로 보여줍니다. 비수정 원본 가격은 주식 분할 뒤 급격히 바뀔 수 있습니다.

`429`는 공급자 지시에 따라 한도 내에서 대기 후 재시도합니다. 주문·계좌·거래 경로는 구현하지 않았습니다.

## 해외 기업의 한글명 보완

worker는 토스 공식 `GET /api/v1/stocks`의 `name`과 `englishName`을 사용해 해외 기업 표시 이름을 보완합니다. 기존 토스 자격 증명을 사용하며 새 환경 변수나 DB 마이그레이션은 필요하지 않습니다. API 키가 없으면 해당 기능을 비활성화하고 기존 이름을 유지합니다.

`sync-toss-stocks` 작업은 매일 07:30 KST에 실행합니다. 작업의 `reason`은 `MANUAL` 또는 `SCHEDULED`이며, 선택적인 `companyIds`는 UUID 1–100개입니다. 기업을 지정하지 않으면 관심 목록을 우선순위 순으로 선택하고, 최근 토스 `PRICE_BARS` 체크포인트의 기업으로 대상을 보완합니다. 최종 범위는 `min(100, TOSS_MAX_SUBSCRIPTIONS)`이며 전체 자산 마스터를 일괄 조회하지 않습니다.

정상 응답은 `STOCK_INFO:<companyId>` 체크포인트에 기록하고 24시간 재사용합니다. 차트 조회와 예약 수집도 이 캐시를 공유하므로, 브라우저의 2초 조회마다 기업 정보 API를 다시 호출하지 않습니다.

해외 기업의 기존 `nameKo`에 한글이 없거나 직전에 토스가 적용한 이름인 경우에만 토스의 공식 한글 `name`을 반영합니다. 별도로 등록한 한국어 이름은 보존하며, 기존 `nameEn`도 덮어쓰지 않고 없을 때만 `englishName`으로 보완합니다. 종목 코드·시장·통화와 `ACTIVE` 상태를 확인하고, 이전에 기록한 ISIN이 바뀌면 적용을 차단합니다. 미지원·불일치 응답으로 이름을 추측하거나 변경하지 않습니다.

원본 응답, 출처 URL, `PRIVATE_DISPLAY_ONLY`, 최초·최근 관측 시각, 기존 기업 이름을 함께 보관합니다. 기능이 배포되어도 모든 기업의 한글명이 즉시 채워지는 것은 아닙니다. 수집 범위와 토스의 지원 여부, 실제 동기화 성공을 확인해야 합니다.

## NAVER 뉴스 인증 오류 대응

`HTTP 401`은 인증 실패이며 공급자 선택, 자격 증명과 API 권한을 확인해야 합니다. 이 오류는 호출 한도 초과(`429`)와 구분하며, 반복 요청만으로 해결되지 않습니다. NAVER Cloud API HUB와 개발자센터는 인증 헤더와 호출 주소, 오류 형식이 다릅니다. [HUB 이관 안내](https://guide.ncloud-docs.com/docs/apihub-migration), [개발자센터 공통 오류 안내](https://developers.naver.com/docs/common/openapiguide/errorcode.md)

1. 키 발급처와 `NAVER_API_PROVIDER`를 맞춥니다. NAVER Cloud API HUB 키는 `ncloud`, 개발자센터 키는 `developers`입니다. 생략 시 기본값은 `developers`입니다. 한쪽에서 인증에 실패해도 다른 공급자로 자동 전환하지 않습니다. [소스별 주소·헤더](SOURCES.md)를 참고하세요.
2. 같은 Application의 Client ID·Client Secret 쌍과 사용 API를 확인합니다. `ncloud`는 **NAVER Cloud 콘솔 → NAVER API HUB → Application → 해당 Application → 인증 정보**의 값을 사용하고 **NAVER 검색 → 뉴스**를 선택합니다. 클라우드 계정의 일반 Access Key·Secret Key를 넣지 않습니다. `developers`는 **Application → 내 애플리케이션 → 해당 앱 → 개요**의 값을 사용하고 **API 설정 → 검색**을 확인합니다. 개발자센터의 검색 권한 미설정은 `HTTP 403`으로도 나타날 수 있습니다. [HUB 설정 절차](https://guide.ncloud-docs.com/docs/apihub-migration), [개발자센터 앱 설정 절차](https://developers.naver.com/docs/serviceapi/search/blog/blog.md)
3. 저장소 밖의 비밀 설정에 `NAVER_API_PROVIDER`, `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET`을 함께 반영하고 [자격 증명 주입 절차](CREDENTIALS.md)에 따라 PM2의 API를 `--update-env`로 다시 로드합니다. 외부 파일을 수정하는 것만으로 이미 실행 중인 프로세스의 값은 바뀌지 않습니다. 기존 `.env`·셸·PM2에 남은 값이 우선하지 않는지 확인합니다.
4. 해당 월의 무료 조건·실제 배정량·운영 재확인 기한을 확인해 `NAVER_NEWS_FREE_MONTH`, `NAVER_NEWS_FREE_REQUESTS`, `NAVER_NEWS_FREE_UNTIL`을 설정합니다. 미확인·만료·한도 소진·사용량 확인 실패 때는 자동·수동 검색 모두 중단합니다. 키 존재와 검색 허용은 별개입니다. [설정 방법과 한도 계산](CONNECTOR-SETUP-PLAN-2026-09-06.md)을 참고하세요.
5. 종목의 관련 뉴스에서 원문 링크와 실제 수집 시각을 확인합니다. 키의 존재, `configured=true`, 빌드 성공만으로 인증 성공을 판단하지 않습니다. 실제 뉴스 요청이 성공해야 복구된 것으로 봅니다. 진단에는 HTTP 상태와 정제한 공급자 오류 코드만 사용하고, 키나 원본 오류 응답을 로그·티켓에 복사하지 않습니다.

## 운영 점검 절차

### GDELT 메타데이터 수집과 오류 대응

GDELT는 `GDELT_ENABLED=true`, 비어 있지 않은 `GDELT_NEWS_DOMAINS`, 지정한 모든 publisher의 저장·표시 정책 승인이 필요합니다. 도메인은 `APPROVED_GDELT_DOMAINS`와 `APPROVED_GDELT_SOURCE_POLICIES`에 등록되어야 하며 정책의 권리 모드도 `STORE_METADATA_ONLY`와 일치해야 합니다. 현재 승인 레지스트리는 비어 있으므로 플래그만으로 수집을 활성화할 수 없습니다. 승인 조건을 충족하면 30분마다 관심기업과 거시경제 주제를 한국어·영어로 검색합니다. 제목·출처·언어·원문 링크만 저장하며 본문·이미지·자동 번역을 추가하지 않습니다. 발견 시각을 기사 발행일로 바꾸지 않습니다. 기존 행과 체크포인트는 장애 대응 목적으로 삭제하지 않습니다. 현재 [이용 권리 계약](RIGHTS.md#sec-ownership메타데이터-뉴스-추가-정책)과 [2026-09-06 배포 기록](DEPLOYMENT-2026-09-06-WATCHLIST-NEWS.md)을 구분해 확인합니다.

`HTTP 429`는 GDELT가 요청을 제한한 상태입니다. 카카오·NAVER 자격 증명과 무관하며 GDELT API 키를 추가하는 방식으로 해결하지 않습니다. worker는 GDELT 요청을 직렬화하고 응답 본문 처리 완료 또는 실패 후 다음 요청까지 최소 5초를 기다립니다. 연결 점검 결과로 수집 성공 시각을 갱신하지 않습니다. 5초 간격은 Orsem의 보수적인 요청 정책이며 공급자가 보장하는 할당량이 아닙니다.

`httpStatus=0`, `transportCategory=timeout`은 HTTP 응답을 받기 전 또는 응답을 기다리는 중 시간 제한을 넘긴 경우입니다. 운영 화면에는 연결/응답 시간 초과로 표시합니다. 2026-09-04 조사에서는 마지막 성공이 19:40 KST, 22:10 점검이 타임아웃이었으며, 한 번의 공개 진단 요청도 약 10.5초 후 `UND_ERR_CONNECT_TIMEOUT`으로 끝났습니다. 이는 해당 시점의 서버→GDELT 연결 경로 지연을 확인한 결과이며, GDELT 전체 장애나 특정 IP 차단의 원인까지 확정한 것은 아닙니다. 이 경우 키 변경이나 반복 요청으로 정상 상태를 만들지 않고 다음 정기 점검 결과를 확인합니다.

2026-09-06 추가 검증에서 TLS 연결에 약 9.9초가 걸리고 기본 10초 연결 제한에 걸리는 경로를 확인했습니다. GDELT의 공식 HTTPS DOC API에만 연결 20초·전체 요청 30초 제한을 적용했습니다. 다른 커넥터의 `HTTP_TIMEOUT_MS`, TLS 검증, 취소 신호와 429 대기는 유지합니다. 진단용 소량 검색의 성공과 운영 수집 성공은 구분합니다. [추가 검증·후속 배포 기록](CONNECTOR-VERIFICATION-2026-09-06.md)

429 응답에서는 즉시 반복 요청하지 않습니다. `Retry-After`가 있으면 그 시각 이전에는 요청하지 않고, 안내가 없으면 1분부터 지수적으로 대기 시간을 늘려 최대 15분까지 적용합니다. 상태 메시지에는 재시도 가능 시각을 KST로 표시하고, 메타데이터의 `retryAt`에는 UTC 시각을 저장합니다. 해당 시각이 지나면 다음 예약·수동 점검에서 요청하며 그 시각에 별도 작업을 자동 생성하지는 않습니다.

점검·검색은 같은 worker 프로세스의 제한 상태를 공유합니다. 이 상태는 메모리에 있으므로 프로세스 재시작으로 초기화되며 여러 프로세스·다른 애플리케이션 사이의 IP 제한까지 조정하지는 않습니다. 반복 재시작으로 재시도를 앞당기지 말고, 같은 서버에서 다른 GDELT 호출이 있는지도 확인합니다. 제한이 계속되면 `DEGRADED` 상태를 유지하며 정상으로 숨기지 않습니다. [GDELT DOC API 공식 안내](https://blog.gdeltproject.org/gdelt-doc-2-0-api-debuts/)

### 공통 점검

1. `/api/v1/operations/sources`에서 커넥터 상태와 신선도를 확인합니다.
2. `/api/v1/operations/queues`와 worker 로그에서 지연·실패 작업을 확인합니다.
3. 화면에서 실패한 특정 공시를 재처리합니다. 한 항목을 복구하려고 모든 수집기를 재시작하지 않습니다. 수집 실행 이력의 일반 재시도는 안전한 실행 이력·큐 재처리 계약이 구현되기 전까지 `501`을 반환합니다.
4. OpenDART `020`에서는 빠르게 재시도하지 않고 다음 할당 구간까지 기다립니다.
5. 파서 결과가 `UNKNOWN`이거나 신뢰도가 낮으면 인증된 원문을 확인하고, 원본 필드를 바꾸지 않은 채 검토를 처리합니다.
6. 메시징 프로세스를 재시작하기 전에 전송 대기함의 적체를 확인합니다.

API 키가 없으면 해당 커넥터만 비활성화되어 `UNCONFIGURED`로 나타납니다. 설정은 있지만 아직 성공하지 않았거나 일시적으로 비정상인 커넥터는 `DEGRADED` 또는 `FAILED`로 나타납니다.

## 환경 변경 절차

환경 값만 변경할 때는 전체 빌드나 DB 마이그레이션을 실행하지 않습니다. [현재 배포 명세](DEPLOYMENT.md)를 먼저 대조해 작업 중인 소스를 운영 실행 파일과 혼동하지 않습니다. 날짜별 기록은 당시 상태를 확인하는 자료입니다.

1. 공용 저장소 루트 `.env`, 설정된 외부 자격 증명 파일, 주입된 프로세스 환경 중 해당 항목을 수정합니다. 비밀 파일 권한은 `0600`으로 유지하고 서로 다른 작업 공간별 `.env`를 만들지 않습니다. 기존 셸·PM2 변수는 `.env`보다 우선합니다. [배포 문서](DEPLOYMENT.md)를 참고하세요. 비밀 값을 PM2 설정, 셸 이력, 스크린샷, 티켓에 넣으면 안 됩니다.
2. 인프라 URL, 저장 경로, 커넥터 자격 증명, SEC 식별 정보를 변경하면 `npm run doctor`를 실행합니다.
3. `VITE_*` 변수를 바꾸면 웹 앱을 다시 빌드합니다. 해당 값은 브라우저 자산에 포함됩니다. 서버·worker 변수는 프로세스 시작 시 읽습니다.
4. 영향을 받는 프로세스만 재시작하고, 알림 전송을 복구하기 전에 `/api/v1/health/ready`, `/api/v1/operations/sources`, `/api/v1/operations/queues`를 확인합니다.
5. `SESSION_SECRET` 교체는 모든 브라우저 세션을 무효화합니다. 관리자의 TOTP를 다시 등록하지 않고 `TOTP_ENCRYPTION_KEY`를 바꾸면 저장된 TOTP 비밀 값을 읽을 수 없으므로 백업하고 교체 절차를 조정합니다.
6. `DISCORD_SERVICE_TOKEN`은 API와 Discord 프로세스에서 함께 교체해야 합니다. MessengerBotR 기기 토큰은 새 연결 코드를 생성하고 등록하여 교체합니다.

이 MVP에서 `APP_MODE`, `PUBLIC_MARKET_DATA_API`, `PUBLIC_ARTICLE_BODY`는 운영 정책 표시 값이며 실행 시점의 권한 통제 수단이 아닙니다. 실제 통제는 인증된 브라우저 경로, 범위가 제한된 봇 토큰, 문서 경로 이탈 방지, 각 레코드의 `RightsMode`로 이루어집니다. 정책 표시 값은 제한적인 상태로 유지합니다.

## SEC·뉴스 복구 운영

현재 실행 명령과 접근 제한 판정은 [SEC 공시 수집 운영](SEC_COLLECTION.md), 커서 복구는 [SEC 누락 복구](SEC_GAP_RECOVERY.md)를 따릅니다. 아래 정책의 도입 당시 검증은 [2026-09-06 결과 기록](SEC_NEWS_IMPLEMENTATION_RESULT_2026-09-06.md)에 보존합니다.

- `SEC_BACKFILL_MAX_REQUESTS=4`, `SEC_FORM4_ENABLED=true`. SEC Submissions recent와 history는 동일 DB 공유 속도 제한·403/429 cooldown을 사용한다. 실제 연락 가능한 SEC_USER_AGENT를 유지한다.
- `GDELT_OVERLAP_MINUTES=10`, `GDELT_MAX_SPLIT_DEPTH=4`. 승인 도메인+코드 정책이 비어 있으면 요청하지 않는다. 현재 승인 레지스트리는 비어 있다.
- `ALPACA_NEWS_ENABLED=false`. 자산 키만으로 News를 활성화하지 않는다. News entitlement·무료 확인 기한·publisher별 저장/표시 승인을 코드 레지스트리에 기록한 뒤 별도로 전환한다.
- `/operations/sources`의 metadata에서 checkpoint, lastFetchedAt, incomplete/truncated, pendingFiles/pendingWindows, windowStart/End, count를 확인한다. 공용 상태에는 정제된 상태·구간·재시도 시각만 표시하고 토큰·원문을 노출하지 않는다. HTTP 요청 성공과 전체 복구 완료는 구분한다.
- XML 실패는 SourceItem ownershipStatus/ownershipRetryAt, 성공은 parserVersion/rawSha256와 별도 EventCluster에서 확인한다. 접수 기록의 완료와 XML 해석 완료는 다르다.
- DB 추가 테이블/마이그레이션 없이 기존 JSON/체크포인트를 재사용한다. 이 변경과 무관한 작업 트리 마이그레이션을 함께 실행하지 않는다.

실제 403/429가 남으면 외부 연결 복구로 보고하지 않습니다. 새 코드의 테스트 통과, HTTP 접근 성공, 공시 접수 저장, ownership 해석 완료를 구분합니다. 재배포는 검증한 wheel과 해당 시도의 명세를 사용하고 기존 SourceItem·EventCluster·체크포인트를 보존합니다. worker만 변경하는 경우 API·웹을 함께 재배포하지 않습니다.
